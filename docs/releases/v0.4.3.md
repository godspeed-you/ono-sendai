# Ono-Sendai v0.4.3 — install a plugin by name, and grant intentions

A patch release on top of v0.4.2. It implements the KUANG/11 plugin installation, resolution and
permission specification (`docs/specs/kuang11/kuang11-plugin-installation-permissions-spec.md`, K11P):
the way a person installs a plugin, decides what it may do, and finds out afterwards what it was
allowed. The capability broker underneath is unchanged and stays the security boundary; what is new
is the human layer above it, and the transaction that makes an install end ready.

> A user grants intentions. KUANG/11 grants capabilities.

## Install by name

- **`install plugin kubernetes`** is the whole ceremony. A short name resolves through the catalogs
  the host knows — the built-in bootstrap catalog and any operator catalog under
  `<config>/kuang/catalogs/` — to a canonical id, a release compatible with this host, and a
  package the host can find locally; `path:` and `git:` references keep working, and a name two
  catalogs answer differently is refused as ambiguous rather than picked.
- **One transaction, ending ready.** Resolve, verify, plan, consent, stage, place, enable, register,
  report. A failure anywhere leaves no package, no enabled state and no grant behind; an upgrade
  keeps the old version until the new one is in place. `get plugin` gains `readiness` — `ready`,
  `needs-permission`, `blocked`, `running` — derived from the lifecycle rather than stored beside it.
- **`get k8s-pod --context prod` works in the same session.** The command registry is refreshed
  after an install, an upgrade or a removal, and a `lazy` package loads on first use.

## Permissions are what a person decides

- **A manifest under `kuang-package/2` declares permissions** — human-titled, with a kind, a phase, a
  risk and the exact capabilities each one maps to — and access profiles (`minimal`,
  `recommended`, and any the package adds). A package with no declaration gets derived
  permissions from its capabilities, so every existing package installs through the new flow.
- **The host classifies every capability, and a package cannot lower it.** Consent classes A–E fix
  which phase and risk a family may claim; a manifest that labels `filesystem.write` as harmless is
  `permission.invalid_mapping` and never runs. Mutation is opt-in everywhere: no recommended profile
  can carry `provider.mutate`.
- **The install prompt speaks plainly.** Recommended access, what is asked only when needed, and
  what is not granted — with `details` one step away, showing every capability, scope, enforcement
  and duration. A native package always states that its tier is not complete filesystem or network
  isolation. Signature, publisher trust and isolation stay separate facts.
- **Just-in-time consent at the moment of use.** A `process.exec` a package needs for a login helper
  is asked for once, with the exact program named: `once`, `this session`, or `always` for that
  program. A script gets `permission.required` with the exact `set permission` line that would
  allow it; nothing is assumed.
- **`get permission <plugin>` and `set permission <plugin> <permission>`** inspect and decide, down
  to the grants underneath; `--profile` switches profiles, `--decision deny` revokes, and `--all`
  shows the automatic and legacy rows. Every decision is remembered in
  `<config>/kuang/permissions.yaml`, every grant it mints carries the permission and the profile
  that selected it, and the audit trail correlates a prompt, its answer and the grant.
- **Upgrades re-consent only for the delta.** A new version that asks for the same permissions
  installs as an update; one that widens a scope or adds a permission names exactly that, and no
  flag accepts a widening a script did not name.

## Unattended rules

`--confirm` accepts the recommended profile and the safe defaults. A profile that adds explicit
mutation needs `--access <profile> --confirm`. A destructive permission is never enabled without a
person. A signed native package from a catalog whose key no trust store enrols is refused unattended
with the policy that would allow it named; an unsigned local package installs with a warning.

## How a package reaches the machine

The acquisition and system-distribution addendum (K11A, ADR-0606 and ADR-0607) answers the
question the permission layer left open. Acquisition may be delegated; trust, permission and
activation may not.

- **Three source kinds, one contract.** A catalog artifact fetched over HTTPS, a local directory,
  or a payload an operating-system package placed under `/usr/lib/ono-sendai/plugin-sources/`.
  `find plugin` shows the kind of every candidate; `inspect plugin` shows the origin an installed
  package was acquired through and whether it is still there.
- **`apt install ono-plugin-kubernetes` grants nothing.** The payload is a candidate; `install
  plugin kubernetes` takes it through the same prompt and transaction as any other source and
  copies it into Ono's store, so `apt upgrade` changes a candidate and never the running package.
  `remove plugin` removes Ono's copy and says the system source remains. A root ordinary users can
  write to is set aside with a warning.
- **Network artifacts are `.kuang` archives pinned to a digest.** Fetched to staging, hashed against
  the catalog's digest, unpacked into the cache, then verified and installed like a directory; a
  cached copy is re-hashed every time. `kuang-sign pack` and `kuang-sign digest` produce what a
  catalog entry needs. Plain `http://` only where an operator catalog declares it.
- **Deterministic selection.** A system copy over a local copy over the network; an installed
  package's own lineage until `--source system|catalog|local` names another; the same version
  with different contents is `plugin.source_conflict`, never resolved by order; two ids under one
  name stay ambiguous however local one of them is.

## Compatibility and migration

- `kuang-package/1` manifests keep loading unchanged, with derived permissions. `kuang-package/2` is
  `/1` plus the optional `permissions` section; the host API is `kuang-host/11.2` and `>=11.1`
  packages still load.
- Existing grants made by hand appear as `legacy` rows under `get permission --all` and keep
  working; nothing is broadened silently, and a revoke by hand is remembered as a deny.
- `grant capability` and `revoke capability` remain as the advanced, raw mechanism, documented as
  such. The relation family gains a `relations` scope key, so a package's contributed relations are
  bounded to its own declared shapes.
- The Kubernetes reference provider moves to the new contract in its own repository, and is the
  worked example throughout the documentation.

The design is recorded in ADR-0600 through ADR-0607; `docs/ACCEPTANCE.md` §4.9 holds the
twenty-four gates and eight security tests of K11P and §4.10 the forty tests of K11A, each proven
by a named test or acceptance case (`220`–`228`).

## Install

The `.deb` and `.rpm` for both architectures are on the release page. To install and make it your
login shell as an unprivileged user:

```bash
sudo apt install ./ono_0.4.3_amd64.deb          # or ono_0.4.3_arm64.deb
sudo dnf install ./ono-0.4.3-1.x86_64.rpm       # or ono-0.4.3-1.aarch64.rpm

chsh -s /usr/bin/ono                             # make it your login shell
```

Verify before you install — the sequence is in `docs/reference/release-verification.md` and in the
README, and it is the one `scripts/verify-release.sh` runs, byte for byte:

```bash
sha256sum -c SHA256SUMS --ignore-missing
cosign verify-blob SHA256SUMS --signature SHA256SUMS.sig --certificate SHA256SUMS.pem \
  --certificate-identity-regexp '^https://github\.com/godspeed-you/ono-sendai/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Or build it: `cargo build --release -p ono-cli`. See the README for configuration, the plugin
layout and login-shell setup.
