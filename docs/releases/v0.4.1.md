# Ono-Sendai v0.4.1 — the boundaries enforce what they claim

The v0.4.1 enhancement specification, **Hardening, Trust & Release Integrity**, implemented on top
of the v0.2 base and the v0.3 and v0.4 layers. Nothing here is a new surface: it is the release
where the things v0.4 said about itself became things it does. A listening agent that claimed to
authenticate its clients now refuses one that proves nothing; a plugin tier that called itself
confined now fails closed when a control cannot be installed; an orientation that quietly read
every object on the machine now reads a bounded view and says how much it left out.

> Bash is a command interpreter. PowerShell is an object shell. Ono-Sendai is a systems interface.

## Trust on a direct link

- **Both ends prove a key.** A TCP agent and its client authenticate each other with mutual TLS
  over ALPN `ono/2`. A client that presents no certificate, a malformed one, or one whose key it
  cannot prove is refused by the TLS handshake — before a single Ono frame crosses, which is what
  §2.2's ordering means. There is no flag, config key or environment variable that starts an
  unauthenticated listener, and the gate scans the whole tree for one rather than trusting a list.
- **Downgrade is impossible and never automatic.** A server that does not ask for a client
  certificate is refused with a stable, non-retryable code, and the client does not try again
  without one — a fallback would show up as a second TCP connection, and a test counts them.
- **A client has an identity of its own.** `~/.config/ono/link_identity.pem`, created `0600` on
  first use and reused across invocations, with an existing `host_key.pem` migrated rather than
  replaced by a second unrelated identity. `ono --print-peer-key` prints the fingerprint an
  operator compares; `ono --agent --print-host-key` still prints the same one.
- **An exposed private key stops the operation.** A `link_identity.pem` anyone else can read or
  write is refused, and the diagnostic names the path and the required mode without printing a
  byte of key material.
- **Authorization is separate from authentication, and both are separate from pinning.**
  `add client-key`, `get client-key`, `set client-key` and `remove client-key` manage an explicit,
  strictly parsed store; a malformed store fails closed at startup rather than reading as empty. A
  newly added client observes and nothing more, an action grant is an exact capability id with no
  wildcards, the offer a client receives is filtered by its policy, and dispatch refuses
  independently of that offer. `get link` shows `authenticated`, `authorized`, `transport_trust`
  and the peer's self-reported identity as four different fields, because they are four different
  things.
- **The agent stays bounded.** Thirty-two concurrent connections, sixteen pending handshakes, four
  per authenticated fingerprint keyed on the fingerprint rather than the address, a handshake
  timeout, and one failing connection that never takes the accept loop with it. Every one of those
  figures is read from a single `Limits` contract, and there is no production constructor that
  leaves one unbounded.

## KUANG/11 fails closed, and says what it is

- **A mandatory confinement control that cannot be installed prevents the exec.** With an injected
  failure of `PR_SET_NO_NEW_PRIVS` or of a mandatory `setrlimit`, the spawn fails with an error
  naming the control, and the marker the plugin would create on startup stays absent.
- **Every security-relevant syscall return value is checked**, and the gate scans the supervisor's
  process-setup code for one that is not, rather than leaving it to review.
- **The tier is a name, not a boolean.** The eleven controls of Appendix D live in one
  machine-readable table with their tier and failure behaviour, every spawn carries a report saying
  per control whether it was applied, skipped as best-effort or refused, and the documentation says
  plainly that the native tier provides no filesystem and no network isolation. It is never called
  a sandbox — a gate check reads every user-facing document and every accepted ADR to make sure.

## Resources, streams and time to first result

- **Materialization is bounded in items and in bytes**, captures share one budget, retained result
  history has per-result and total byte ceilings and says when it truncated, and an operation that
  needs finite input refuses an unbounded one immediately instead of waiting for a stream that
  never ends. Every limit is one row in one registry, range-checked at load, and readable with
  `inspect limits`.
- **`each` streams.** It consumes and emits incrementally, works against an unbounded source, and
  keeps control flow, backpressure and cancellation exactly as the language defines them.
- **All four of §33.2's time-to-first-result targets hold** on the release reference environment,
  measured by `cargo xtask perf` at twenty iterations against a recorded baseline with six metrics
  per benchmark:

  | target | budget | v0.4.0 | v0.4.1 |
  |---|---|---|---|
  | cached `look`/`near` first result | 50 ms | 1.0 ms | 1.1 ms |
  | Profile M spatial query first result | 150 ms | 595 ms | **122 ms** |
  | Profile M `map --live` first frame | 500 ms | 805 ms | **220 ms** |
  | Profile L `map --live` initial progress | 1 500 ms | 3 514 ms | **572 ms** |

  The last of those was a hundred thousand socket records absorbed before anything was drawn. An
  orientation now reads `limits.orientation_objects` of a target and the provider states the
  population beside the bounded answer, so the count you are shown is still the count that is
  there. Where a count cannot be kept true it is not invented: `count` is null and the group says
  why.

## Release integrity

- Every required GitHub Action is pinned by commit SHA and every release-critical image by digest;
  the toolchain and tools are exact and the dependency fetch is reproducible.
- Each publishable artifact is **built twice in clean environments that disagree about locale,
  timezone, umask and directories, and compared byte for byte**.
- `SHA256SUMS` covers every downloadable artifact in deterministic order, verified in both
  directions, with signed provenance binding seven fields to each artifact digest — and the bytes
  that were tested are the bytes that are published.

## The numbers

The workspace is 31 crates and about 3 500 outcome tests, the containerised acceptance suite is
146 cases run against the real `ono` binary as an unprivileged user with no network, and 576
architecture decisions are recorded in `docs/adr/`. `docs/ACCEPTANCE.md` §4.8 holds this
tranche's definition of done in 118 boxes, each ticked by a named automated proof and none by
judgement; `xtask/tests/hardening_evidence.rs` resolves every proof the checklist names on every
gate run.

## Known, measured, not hidden

**A selector miss at Profile M costs 900 ms against §36.1's 250 ms target.** `enter no-such-place`
has to sweep every acquisition class before it can say `not_found`, and the last class is the
systemd enumeration; a hit that resolves out of the index costs 197 ms. §36.1's MUST — that a miss
not be more expensive than a hit *solely because the system scans an unnecessarily complete global
candidate set* — is met by the cheapest-first sweep, and the wall-clock target is not. Bounding the
sweep is not the fix: an `enter` that stopped early would report `not_found` about something that
is there. It is measured, recorded in the baseline and on the board, and it is a latency defect
rather than a wrong answer.

**Two boxes of `docs/ACCEPTANCE.md` §4.8 were open until this release closed them**, and they
closed the only way they could: keyless signing needs an OIDC token that exists only inside a run
of the release workflow, and verifying one needs Sigstore over a network the acceptance container
is denied (§40.2). This tag's run signed `SHA256SUMS` and `build-provenance.json` under the
identity `…/release.yml@refs/tags/v0.4.1`, verified both before drafting anything and again before
making the release visible, and attached nine assets each byte-identical to what was verified
(ADR-0529, ADR-0542, ADR-0545).

**The first attempt at this tag published nothing, and that was the harness working.** It signed,
it verified, and then it failed to draft the release: the publishing script asked the GitHub CLI
to act from the artifact directory, which the workflow keeps beside the checkout rather than
inside it. §49.4's order — verify, draft, upload, check the inventory by digest, publish — put the
failure before anything existed, so there was no draft and no half-populated asset list to clean
up. ADR-0579 is the fix, and finding that defect is exactly what a release-integrity tranche's
last two boxes are for.

## Notes for upgrading

- **A remote client now needs to be authorized.** An agent accepts only clients whose key is in its
  `authorized_clients` store; `ono --print-peer-key` on the client and `add client-key <fingerprint>`
  on the agent is the whole bootstrap. `docs/reference/remote-migration.md` walks the five paths.
- **`ono/1` is gone.** A v0.4.0 client cannot speak to a v0.4.1 agent and will not silently fall
  back; upgrade both ends.
- **`~/.config/ono/host_key.pem` becomes `link_identity.pem`** on first use, and the fingerprint
  does not change. An exposed key file is now a refusal rather than a warning.
- **An orientation of a place with more than 16 384 sockets shows no listener or connection count.**
  `get socket | count` is unbounded and exact; it is the orientation that is budgeted.

## Install

`.deb` and `.rpm` for x86_64 and aarch64 are attached below. Each is installed into fresh Debian
and Fedora containers on both architectures before it is published — as root and as an
unprivileged user whose login shell is `ono`:

```bash
sudo apt install ./ono_0.4.1_amd64.deb          # or ono_0.4.1_arm64.deb
sudo dnf install ./ono-0.4.1-1.x86_64.rpm       # or ono-0.4.1-1.aarch64.rpm

chsh -s /usr/bin/ono                             # make it your login shell
```

Verify before you install — the sequence is in `docs/reference/release-verification.md` and in the
README, and it is the one `scripts/verify-release.sh` runs, byte for byte:

```bash
sha256sum -c SHA256SUMS --ignore-missing
cosign verify-blob SHA256SUMS --signature SHA256SUMS.sig --certificate SHA256SUMS.pem \
  --certificate-identity-regexp '^https://github\.com/godspeed-you/ono-sendai/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Or build it: `cargo build --release -p ono-cli`. See the README for configuration, the plugin
layout and login-shell setup.
