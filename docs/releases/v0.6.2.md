# Ono-Sendai v0.6.2 — the verification foundation

A foundation release on top of v0.6.1. It changes what the shell is built from and how it is
proven, not what it does: the binary is 22 MB instead of 46, a budget keeps it there, KUANG/11
components are compiled once at install instead of at every load, a static core build exists for
containers and embedded Linux, and the test suite, the acceptance harness and the release tooling
give the same answer on a loaded machine as on a quiet one. The GitHub milestone `v0.6.2`
("Verification Foundation") is the release inventory. It has no narrative specification, and
ADR-0862 records that each of its 24 issues is a requirement whose exit test decides it.

> Establish a reliable test, build and release foundation before making larger semantic changes.

## A smaller shell, and a budget that keeps it small

The release profile optimises for size: `opt-level = "s"` with fat LTO, still unwinding on panic
(#124). The Cranelift compiler left the shell (#126, below). Together they take the stripped
`x86_64` binary from **46,094,688 to 22,151,072 bytes** (the packaged binary; `aarch64`: 19,418,112, measured one
review round earlier).
On one tree, on a quiet machine, the new profile is 4–10 % slower in CPU-bound first rows
(`process.enumeration`, `spatial.look` cold, `map_first_frame`), equal in cold start (p95
5.6–6.4 ms against 6.0–6.3 ms), and holds every §34 target. The performance baseline was measured
again for this tree, and every row that moved says why (ADR-0926).

The stripped size is now a measured figure with a budget per binary and target triple beside the
other limits (`docs/contracts/hardening/limits.yaml` → `build_budgets`): `ono` 24,350,304 bytes on
`x86_64` and 21,359,924 on `aarch64`, `kuang-compile` 8,045,823 and 6,151,174, and under
8,000,000 for the static core build — each the measured figure plus ten percent. They are
enforced where the bytes that ship are made: `scripts/package.sh` checks every packaged binary
against the budget of its triple on both architectures and refuses a triple no budget covers,
`scripts/build-core.sh` the core binary, CI's image build the image's `ono`, and the gate a
current local release build. `xtask metrics` records the figures in
`docs/baselines/binary-size.yaml` and the README, CI fails a push whose shipped binary moved more
than one percent from that record, and the release input manifest carries the budgets and the
record together with the commit that wrote it (#125, ADR-0864, ADR-0866 … ADR-0868).

The seven minutes of CI's release build are a cold dependency build plus a serial tail: the shell
at one codegen unit, then the LTO link. The packaging job now publishes cargo's timing report for
every push, and the release tool, which is not shipped, builds at its own profile (#218, ADR-0865).

## KUANG/11 components are compiled once, at install

`ono` no longer links a compiler. `install plugin` runs the SDK's new `kuang-compile` on a
component package once, which writes the engine's native form into a store only its owner writes;
the shell maps that artifact and refuses a missing, stale, foreign or untrusted one with
`load.component_not_compiled` (Ono-Sendai-K11105), naming the exact `kuang-compile` command to run.
An artifact is compiled for the architecture, not for the machine, so an image or a system store
built on one host loads on every other of its kind, and for the exact wasmtime release, so a shell
upgrade that changes the engine invalidates it. The shell opens the artifact once, without
following links, checks that it and every directory above its store belong to root or to the
user and that nobody else can write them, and deserialises the very bytes it checked. Stores and
the compile tool come from the session's environment, and install refuses a `kuang-compile` on a
relative `PATH` entry. Both packages ship `/usr/bin/kuang-compile` beside `/usr/bin/ono`, and
`SECURITY.md` names the new trust boundary. (#126, ADR-0870, ADR-0905, ADR-0914 … ADR-0917;
`docs/MIGRATION.md` §10)

## A core build for containers and embedded Linux

`cargo build --release -p ono-cli --no-default-features --features core --target
x86_64-unknown-linux-musl` builds the object shell alone — the language, the evaluator, typed
pipelines, the native commands, the Linux and network providers — as one static binary of
7,063,744 bytes. A command of a tier it leaves out refuses with `resolve.not_in_build`
(Ono-Sendai-E0104); `get service` refuses with the same `provider.unavailable` a full build gives
on a host without systemd; `help` and completion show only what the build carries, and `ono
--version` names the profile. `scripts/build-core.sh` builds and checks it, 27 acceptance cases
run against it in a `FROM scratch` image with a static busybox for the harness, the image as it
ships is started and checked as its own user, and CI runs the whole core test suite, the build and
the profile on every push. The default build is the full product, unchanged. (#127, ADR-0910 …
ADR-0913, ADR-0923 … ADR-0925)

## Tests that hold on a busy machine

- A test that compared two readings of the live host now reads it once, owns the fixture it
  reads, or brackets the second reading: `near`, whose own stream is counted in the same run that
  notes its rows (#165), the service count behind a bounded orientation, now against a service
  manager the test runs itself (#155), the mount table, the type-filtered map and the completion
  that waited for an echo instead of a place (#215) (ADR-0880).
- Fixed sleeps and wall-clock bounds became observations: a background job is waited for, not
  slept on (#164); a file event is judged by where it came from, not by how long the machine took
  (#160).
- A budget that measures the machine says which machine it is measured on, and cannot excuse a
  hang: a silent Profile L live map on a busy machine is asked again with a longer watchdog and
  fails if it stays silent (#166, ADR-0881, ADR-0883); case 152 holds each row to its budget at
  the fastest run unless the same run shows the machine loaded, fails a run of `ono` that did not
  succeed, and matches its verdicts line by line (#189, ADR-0882, ADR-0884).
- The two `change_claims.rs` tests reported at 31 s take under a second; the FIFO hypothesis was
  refuted by timing and `strace`, and a recurrence now fails within 25 s instead of passing
  at 31 (#141).
- The suite leaves nothing behind. Scratch space lives in cargo's build layout, found at run time
  and never guessed, and Unix sockets get a short private directory of their own (#143, ADR-0890,
  ADR-0895, ADR-0896); a test script or program is written by a process of its own, so `exec` never
  meets `ETXTBSY` (#188, ADR-0891); an overrunning or failing test ends the whole process tree it
  started — through pidfds, children before parents, so no reused pid is signalled — and every
  pseudo-terminal session a suite starts is owned that way (#162, #204, ADR-0892 … ADR-0894).
- `skip-check` names every permitted skip a CI run takes and holds its category, and the core
  suites' skips are held to the register too (ADR-0885).
- A key typed together with a terminal resize was stranded: crossterm's default reader answered
  the resize and never looked at the terminal again, so the paused live map ignored Esc. The shell
  now reads the terminal with crossterm's level-triggered reader (ADR-0920); the suite that failed
  8 of 20 runs under load passed 40 of 40.

## Release tooling that cannot compare against yesterday

- `release-check.sh` builds into a directory it owns and qualifies a committed tree only;
  `package.sh` refuses any file in its release directory it did not write, builds both packages
  from exactly the tracked files, and packages the binaries its build step wrote (#145).
- The RPM is byte-reproducible: every member carries the epoch, whatever age its source file has
  (#146, ADR-0902).
- A release tag must name the workspace version (`scripts/release-version.sh`, in release.yml).
- `xtask perf` refuses a row sampled by a build other than the one it claims, reports a figure
  from another build as uncomparable, reads the load before each row and scales its allowance to
  the cores, and exits 3 on a regression and 4 when it could not adjudicate, with a summary line
  (#151, #169, ADR-0904, ADR-0908, ADR-0909).
- Each checkout builds its acceptance image, and package validation its test image, under a tag of
  its own; one lock per checkout, kept in the repository where every user of the checkout finds
  it, decides who removes them, and an image built for later runs is kept (#185, ADR-0901,
  ADR-0907, ADR-0919).
- CI keeps the acceptance image's filesystem stage in a buildx layer cache instead of downloading
  it from the Ubuntu archive on every run, rebuilds it at least weekly, and says whether it came
  from the cache; a cache miss still builds (#139, ADR-0903, ADR-0918).
- `THIRD-PARTY-LICENSES` owes exactly what the shipped binaries link, each resolved on its own
  (ADR-0906), and AGENTS.md names the sub-branch form git can create, which CI now builds (#196,
  ADR-0900).

Found and fixed on the way: `kuang-sign pack` wrote a file with holes as a GNU sparse entry the
host refuses to unpack; the gate did not select the packaging suite when `THIRD-PARTY-LICENSES`
moved; a redirected `inspect plan --resolution` cut a deep path inside its file name, and now
shortens it at its start; tests that read rendered output or assumed a directory outside any
checkout depended on the checkout's depth.

## An independent review, and what it changed

After the first integration an independent review — four focused passes that had not written the
code, over the issues, the diff, the tests, CI and the run's evidence — found two security defects
in #126 (a path-based trust check with a window between check and load, and artifacts that
survived a wasmtime patch release), budgets not enforced where the packages are built, verdict
rules in case 152 and the Profile L test that could pass or skip a real regression, and a dozen
smaller gaps in the harness, the release scripts and the core build. Every finding was fixed in
its own commit with its own test, or is recorded in `docs/STATE.md` with the reason it is outside
this release; the ADRs from ADR-0866 on are that round.

## Compatibility

Nothing a v0.6.1 configuration or script relies on changes. A component package installed before
v0.6.2 has no compiled artifact yet: its first load refuses with the `kuang-compile` command to
run, once (`docs/MIGRATION.md` §10). A shell built from source needs `kuang-compile` beside it to
install component packages (README, *Installing it*). A component store below a directory other
users can write is refused as `untrusted`, with the directory named; an account whose home
directories are writable by its own private group is accepted (ADR-0915).

## Install

The `.deb` and `.rpm` for both architectures are on the release page:

```bash
sudo apt install ./ono_0.6.2_amd64.deb          # or ono_0.6.2_arm64.deb
sudo dnf install ./ono-0.6.2-1.x86_64.rpm       # or ono-0.6.2-1.aarch64.rpm

chsh -s /usr/bin/ono                             # make it your login shell
```

Verify before you install — the sequence is in `docs/reference/release-verification.md` and in the
README, and it is the one `scripts/verify-release.sh` runs, byte for byte:

```bash
sha256sum -c SHA256SUMS --ignore-missing
cosign verify-blob SHA256SUMS --signature SHA256SUMS.sig --certificate SHA256SUMS.pem \
  --certificate-identity-regexp '^https://github\.com/godspeed-you/ono-sendai/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```
