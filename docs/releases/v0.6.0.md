# Ono-Sendai v0.6.0 — a change is a thing before it is an event

`docs/ACCEPTANCE.md` §4.12 is this tranche's definition of done, derived from the specification's
own fifty acceptance scenarios, its twenty release criteria, its eighteen core invariants and its
twenty-two destructive-recovery safety facts. Every ticked box names an automated proof that runs
in the gate or in the acceptance container, and every box still open is listed under *Recorded
exclusions* below (§66.9). A reader learns what is unfinished here or nowhere.

`docs/specs/ono_sendai_shell_spec_v0.6_prospective_change_protection_recovery.md` is the
specification.

> A shell is unusually close to mutations. Traditional shells treat the command line as the point
> of commitment; v0.6 puts a semantic layer between intent and irreversible effect.

## What the tranche is

v0.4 gave the session a place, v0.5 gave it an instant, and v0.6 gives it a *proposal*. A
mutation becomes a `ChangePlan`: an object that can be inspected for what it would touch, what
would protect it and what would remain irreversible — before any of it is made real, and, where
the evidence supports it, recovered afterwards.

The lifecycle is `Plan → Impact → Protect → Apply → Observe → Verify → Recover`, and protection
and recovery are first-class parts of it rather than something bolted on the end. Nineteen plan
states, thirteen commands, eleven machine-readable registries and eleven crates hold it up.

Four sentences are the whole of it, and each one is a type rather than a convention:

- **Planning changes nothing.** `plan` reads providers, reads the topology, asks the recovery
  providers what they *could* offer, writes one row to the store and prints `PLAN NOT EXECUTED`.
  Case `280-plan-creates-nothing` checks the file, its modification time and the recovery store
  before and after.
- **Protection is coverage, not a boolean.** Appendix A's algorithm runs per mutation domain, and
  `PROTECTED` is reachable only when every persistent thing the plan changes has a validated way
  back. An unknown domain caps the answer at `PARTIALLY_PROTECTED` (Appendix A.7), and the
  exclusions are shown beside the word — always (§62.6).
- **Recovery is planned, then performed.** `recover` produces a `RecoveryPlan` and restores
  nothing. It compares the recovery point against the world, prefers the method that loses the
  least, and names every newer object it would destroy before it will destroy one.
- **Verification is separate from execution success.** A command that returned zero has proved
  that it returned zero. Every plan that mutates carries a contract that can be answered, with a
  timeout that is never infinite and never read as a pass.

**A change over a remote link.** Inside `enter link`, `plan` freezes its targets through the
link's providers and records the link as their host (§7.1, §29.1, ADR-0848). Such a plan applies,
protects, verifies, rebases and resumes only inside that link; anywhere else it is refused with
`change.precondition_failed`, naming the host. Protection is analysed per host, and the matrix
says that no recovery provider of this build runs on the far side (§29.2). An action whose link
drops before it answers is `UNKNOWN` and the plan stays `applying` (§29.3, Appendix F.2), and
`recover` says which host it cannot proceed on (§29.4). A plan that stops the interface a network
link leaves by is CRITICAL (§34.2, ADR-0850). A file or a directory inside a link is refused,
because its path would be resolved against this machine.

## The two providers that exist to be got right

**ZFS** (§13) is a first-party reference provider because its snapshot semantics map naturally to
protected change — and because §13.4 is a trap: a snapshot of the root dataset does not protect a
separate child dataset, however the paths nest. §13.6 is the other one: a rollback that would
destroy newer snapshots, bookmarks or clones is enumerated and gated, never silently forced. The
provider's twelve §56.1 safety facts each have two tests: one that the fact is established, and
one that a fact that could not be established blocks.

**Btrfs** (§14) opens by forbidding itself being modelled as if it were ZFS. §14.3 is the fact the
whole provider turns on: snapshots are *not* recursive across nested subvolumes, so a snapshot of
a parent contains an empty directory where a nested subvolume was. §14.4 forbids presenting a
generic in-place rollback primitive that Btrfs does not have; what it has is three workflows, and
the plan names which one it would run and whether it needs the filesystem offline or a reboot.

**A file and configuration provider** (§15) is what a host with neither gets. It claims
`byte-consistent` and nothing wider, puts its copies where other users cannot read them, restores
through temp-file, fsync and rename, and lists the metadata it does *not* put back beside the
coverage it does (Appendix C.7).

Both snapshot providers parse **real recorded output**: `scripts/fs-fixtures.sh` builds a pool and
a filesystem on loop devices inside a container and records what `zfs` and `btrfs` actually print,
and the deterministic suites read those bytes. Where a test needs a situation the recorded pool does
not present — a clone of a newer snapshot, an orphaned bookmark, a degraded pool, a `zfs allow`
delegation — the row is composed onto recorded output and labelled as composed in the test, and the
real scenario is in the generator for an operator who chooses to create pools. The destructive
paths run against filesystems the suite creates and destroys, never a production one (Appendix
G.3).

## Decisions

Thirty-eight ADRs, `ADR-0800` through `ADR-0837`. Four of them record a deviation from the
specification, and each cites the sentence it departs from:

- **ADR-0801** — §45 fixes the error *names* and leaves the numbers open; the change, recovery and
  transaction families take `E1701`–`E1729`, `E1801`–`E1820` and `E1901`–`E1902`, the lowest free
  blocks. Fourteen refusals beyond §45's list are recorded with the sentence that required each.
- **ADR-0802** — §46.6 asks for `ono.verification-result/1`, which v0.2 §31.36 already holds for
  `verify plugin`. The change one is `ono.change-verification/1`.
- **ADR-0803** — §5's `@plan` does not lex: `@` is v0.2 §19.4's current-value reference. §36.4's
  three normative spellings work verbatim, and `plan … | apply` falls out of a plan being an
  ordinary value.
- **ADR-0815** — §17.2's four modes are not a scale. `require` and `maximize` are different
  properties, and the order that totalises them puts the failing-closed one on top. The one pair
  that produces a narrowing is reported rather than silent, because §53 forbids configuration
  weakening a plan quietly.

Five more were written after the implementation looked finished, because driving the binary found
things reading the code did not:

- **ADR-0817** — a sealed plan applies once, and that is a statement about the *store*. The state
  is written at each transition, so an interrupted run is found where it stopped.
- **ADR-0818** — a recovery plan's actions are run like any other, and its verification is written
  in a form the shell can answer.
- **ADR-0819** — §17.1's protection actions are in the plan, where an operator can refuse them.
- **ADR-0820** — the plannable operations are read from the contract. A hand-written table in the
  shell had eleven of the registry's forty-six.
- **ADR-0821** — one ledger per process, and §17.2's subtype is what `timeline` prints.

`docs/dogfood/v0.6-2026-09-10.md` is the session that produced ADR-0817 to ADR-0820; ADR-0821 came from the timeline work that followed it.

Eleven more came out of the final audit, which read the implementation against the specification
requirement by requirement and drove every guarantee through the binary:

- **ADR-0822** — a recovery plan is stored with its analysis and analysed again before it runs. A
  loss that appeared after `recover` refuses whatever was accepted, §24.5's gate decides, and every
  restore goes to the provider that made the recovery point — which corrects ADR-0818's statement
  that the first-party providers planned their restores as recovery operations: ZFS never did, and
  now it does not matter.
- **ADR-0823** — an opaque action is unknown-reversible, not irreversible; `--opaque` is §6.3's
  acknowledgement.
- **ADR-0824** — a settled action carries the instant it settled, which is what tells the plan's
  own write from a later edit.
- **ADR-0825** — `apply` keeps the protection the sealed plan showed or stops as `PREPARE_FAILED`.
- **ADR-0826** — change settings are read key by key, and an unreadable one is reported.
- **ADR-0827** — a copy never writes through a symlink at its destination (§43.5).
- **ADR-0828** — a restore reports the assets it created; provider settings carry over whole.
- **ADR-0829** — three ZFS judgements: a rollback that loses nothing needs no acceptance, `zfs
  allow` is read as an adapter fallback, and an unhealthy pool is refused where the mode decides.
- **ADR-0830** — `apply` confirms only when gated, a copy is verified by its bytes, `verify`'s
  verdict is in its results, and the session states the authority it actually holds.
- **ADR-0831** — early protection is assessed object by object (§18.2), and §19.4's policy flag
  waives the risk acknowledgement it names.
- **ADR-0832** — `plan --auto-recover` is accepted and rejected at seal, naming the §26.3
  conditions this build cannot meet.
- **ADR-0833** — corrections to the first twenty-two decisions, each claim quoted beside what the
  code does, where the audit found a decision stated more than the code delivered. Two of them
  were made true instead: an ambiguous reference now states the prefix width that tells the
  candidates apart, and the Btrfs tool runner now waits a bounded time, as the ZFS one did.
- **ADR-0834** — `recovery.zfs.allow_destructive_rollback` and `prefer_selective_restore` decide,
  and a preference never makes recovery more destructive than Appendix C.1 permits.
- **ADR-0835** — an explicit `--protection` may lower the built-in default, never a configured
  mode; `protect --refresh` is gone and `verify --timeout` caps every check.
- **ADR-0836** — Appendix H's profiles are selectable with `change.profile`, only tighten, and
  expand with `get config --profile`.
- **ADR-0837** — a KUANG/11 VM-snapshot provider states whether its snapshots include memory, and
  a package that does not is refused at load (§16.2).

## Safety and privacy

Every recovery provider runs its tool through a runner that takes a program and an argument
vector. There is no variant that takes a command line, so a dataset name containing a semicolon is
a dataset name containing a semicolon (§12.3, §2.17).

Nothing destructive runs on the strength of a plan alone. A recovery that would discard newer state
needs `--accept-newer-state-loss`, is analysed again at `apply`, and is carried out by the provider
that made the recovery point, which re-proves §56.1's facts and refuses a `-R` in any spelling at
the moment of the act. A target swapped for a symlink after the seal is drift, and a copy opens its
destination without following a link (§43.5). The executor is told the authority the session
actually holds — its effective uid and capability set — rather than assuming it may do everything
(§43.3).

A recovery asset's *metadata* travels — scope, consistency, cost, retention — and its contents do
not. The file provider exposes no accessor returning captured bytes, the renderer cannot reach a
provider, the store is `0700`/`0600`, and a declared secret is replaced before the record reaches
the database (§44).

Cleanup never outruns recovery policy. Removing an asset a retained plan still depends on is
refused by name, a preview says which plans would become unrecoverable, and the assets of a
failed, degraded or recovery-failed plan are held out of ordinary retention entirely (§2.15,
§37.2, §37.3).

KUANG/11 plugins need no manifest change. the eleven change and recovery capabilities of `docs/contracts/capabilities.yaml` (§48.3 names seven of them as examples) go
through the existing broker; there is no second permission system. A package claiming
`application-consistent` without `recovery.quiesce` is `package.invalid` before any of its code
runs, and §16's optional providers — LVM, VM, container, database — are that surface rather than
first-party crates (ADR-0812, ADR-0816).

## Compatibility

v0.2 through v0.5 behaviour is unchanged: typed pipelines, external programs, adapters, spatial
navigation, maps, remote links, KUANG/11, the temporal coordinate, prompt and PTY behaviour. The
whole earlier suite and every earlier acceptance case run unmodified, which is what
`scripts/release-check.sh` requires before it prints anything.

A shell that never types `plan` behaves exactly as v0.5 did. Seventeen new settings default to
§53's reference configuration; the one that matters most, `change.default_protection`, is
`prefer`, and protection is only ever attempted where a provider can create a bounded-cost asset
without materially changing the operation.

## Install

The `.deb` and `.rpm` for both architectures are on the release page. To install and make it your
login shell as an unprivileged user:

```bash
sudo apt install ./ono_0.6.0_amd64.deb          # or ono_0.6.0_arm64.deb
sudo dnf install ./ono-0.6.0-1.x86_64.rpm       # or ono-0.6.0-1.aarch64.rpm

chsh -s /usr/bin/ono                             # make it your login shell
```

Verify before you install — the sequence is in `docs/reference/release-verification.md` and in the
README, and it is the one `scripts/verify-release.sh` runs, byte for byte:

```bash
sha256sum -c SHA256SUMS --ignore-missing
cosign verify-blob --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/godspeed-you/ono-sendai/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  SHA256SUMS
```

Or build it: `cargo build --release -p ono-cli`. See the README for configuration, the plugin
layout and login-shell setup.
