# Dogfooding v0.6 — 2026-09-10

The session `docs/ACCEPTANCE.md` §4.12 asks for, and the evidence behind ADR-0817 through
ADR-0820: real use of the change lifecycle on a host nobody prepared for it, recorded as what was
asked, what the shell answered, and what was wrong with the answer.

**Host.** The development workstation, `PC12-Ubuntu`: Ubuntu, 8 cores, ext4 throughout — no ZFS
pool and no Btrfs filesystem, so the file provider of §15 is the honest scenario and the two
snapshot providers were exercised against recorded real output and against loopback filesystems
in a container instead (`scripts/fs-fixtures.sh`, `crates/ono-recovery-{zfs,btrfs}/tests/real_*.rs`).
**Binary.** `target/debug/ono`, a debug build, with `HOME` and every XDG root pointed at a scratch
directory so the plan store written here is nobody else's.

**Verdict, first.** The lifecycle works end to end — `plan` changes nothing, `apply` protects
before it mutates, `recover` produces a plan and performs nothing, and applying that plan restores
the object and verifies the restore against the digest the archive recorded. It did not work when
the session began. Six defects are below, four of them things a reader of the code would have
called correct: every one was found by running the binary and looking at what it printed.

---

## What was asked, and what came back

```
plan copy file <source> <target> --overwrite
apply <plan>
recover <plan>
apply <recovery-plan> --accept-newer-state-loss --confirm
```

The final state of that sequence is the file as it was before the change, a passing
persistent-state verification, and two recovery assets in the store. Along the way:

- `plan` printed the coverage matrix, the risk class with the rule that produced it, the
  verification contract it would ask afterwards, and `PLAN NOT EXECUTED`. Nothing was created:
  the recovery store directory did not exist until `apply` ran.
- `protect --confirm` refused without the flag, naming it, and §40.3's sentence about scripts.
- `recover` printed `NEWER STATE AT RISK — 1 object changed after the recovery point`, the
  restore method, the metadata it would *not* put back, and `RECOVERY NOT EXECUTED`. The file was
  untouched afterwards.
- `remove recovery <ref>` refused without `--confirm` and named `--dry-run` as the way to see
  which plans would become unrecoverable.

## 1. An applied plan applied again — blocking

`apply` mutated the target, verified it, and left the store holding `sealed`. A second `apply` of
the same plan mutated the target a second time. §2.7 — *a sealed plan applies once* — is a
statement about the store, and nothing wrote the state to it.

Everything else about the run was right: the executor reached `VERIFIED`, the action statuses were
persisted, the recovery asset was created and validated. Only the one column nobody wrote.

Fixed in ADR-0817: `PlanStore::record_state`, written at each transition rather than at the end,
so an interrupted run is found at `PREPARING` or `APPLYING` and §41 has something to resume from.

## 2. A refusal reported as a success — blocking

Once §1 was fixed, the second `apply` refused — and printed `APPLY 1/1` above the refusal, because
`ApplyOutcome::is_success` read the plan's state and the plan was `VERIFIED`, from the run before.
`has_mutated` had the same shape and answered "the system may have changed" about that earlier run.

§2.14 and §62.9 are about not reading a success from the wrong evidence, and this was the same
mistake one layer up. Both are now facts about the run: `is_success` is false whenever there is an
error, and `has_mutated` is `FailurePoint::may_have_mutated`.

The refusal's help was wrong too. `change.plan_not_sealed` explained §4.2's draft to an operator
whose plan had already run; it now chooses its sentence from the state the plan is actually in.

## 3. A recovery plan could not be applied — blocking

`apply <recovery-plan>` failed at its first action, on every provider, with
`change.action_not_plannable`. The CLI's executor bridge answered every `Execution::RecoveryOperation`
with a refusal whose comment claimed recovery is carried out "at PREPARE and RESTORE, never as a
plan action of its own". PREPARE was true. RESTORE had no other route, so §5.8's second half did
not exist.

Behind it, the recovery verification read *"the SHA-256 of `<path>` is the digest the archive
recorded"* — a sentence, not a condition anything can observe. §62.9 names exit-code verification
as a failure mode; a contract nobody can answer is the same failure with an extra step.

Fixed in ADR-0818: `RecoveryOperation` routes to the provider that named itself in it, and the
contract is `file <path>` / `sha256 == <digest>`, which the shell answers by reading the file.

## 4. Thirty-five of forty-six operations were not plannable — blocking

`plan kill process <pid>` answered:

> `ono.process.kill` declares none of that: this build knows it as a command and not as a mutation
> it can describe.

`docs/contracts/change/actions.yaml` declares it in full — three effects, all irreversible, an
idempotency class, recovery semantics and a verification contract. `ono-cli` was not reading the
registry. It carried its own eleven-row table, and the other thirty-five operations were refused
with a sentence about a contract that exists.

Fixed in ADR-0820. `plan kill process <pid>` now produces: three mutation domains all
`UNPROTECTED`, three irreversible effects, `HIGH` risk on irreversibility, and `not recoverable`
naming the subject — §33.1 and §35 reaching an operator for the first time.

Two smaller things fell out of it. Freezing asked every provider for a `name` field, so
`process 4211` — selected by an integer `pid` — resolved to nothing; and an operation that
*creates* its object had nothing to freeze, so `add user alice` was refused for naming a user who
does not exist, which is the point of the plan.

## 5. §17.1's protection actions were not in the plan — material

§17.1's second clause is *"include protection actions in the plan"*. The plan held only the
mutating action; the protection lived in a parallel list the executor worked from. An operator
inspecting a plan before applying it saw one action for a run that would take two, and the
progress display printed `PREPARE none` beside a recovery point that demonstrably existed.

Fixed in ADR-0819.

## 6. Four display defects that state something untrue — material

Each of these is a renderer saying something the engine did not.

- **`metadata coverageAppendix C.7: …`** — a label eighteen columns wide in a sixteen-column
  field, with no separator. Two cells presented as one word.
- **`no-recovery-requiredUNPROTECTED`** — the same defect in the coverage matrix, where the
  objective field was a fixed eighteen columns and the word is twenty.
- **`covered`** as the heading over three `UNPROTECTED` rows. §2.5 forbids overstating coverage,
  and the heading is part of what states it. It is `by domain` now.
- **Truncation with no marker.** `/srv/app/config` and `/srv/app/config.bak` cut to the same
  column are the same line. v0.2 §13.3 requires the cut to be visible and `ono-render` already
  has a marker; the change renderer was not using it.

## What this session did not exercise

- **ZFS and Btrfs on this host.** There is neither. The providers' semantics are covered by the
  recorded-output suites and by the loopback tests, and §4.12's boxes for the two real-filesystem
  cases are proven in the container rather than here.
- **Remote change.** One host.
- **A KUANG/11 recovery provider.** None exists yet; §16's optional providers are the plugin
  surface (ADR-0812).
- **Multi-day retention.** §37.1's twenty-four hours did not elapse during the session; the
  retention logic is covered by `ono-change-protection/tests/retention.rs` against a supplied clock.
