# Dogfooding v0.4 — 2026-08-28

The session v0.4 §52.3 requires, and `docs/ACCEPTANCE.md` §4.7.2's *product-experience* box and
ADR-0137 make evidence: real use of the shell on a host nobody prepared for it, recorded as what
was asked, what the shell answered, and what was wrong with the answer.

**Host.** The development workstation, `PC12-Ubuntu`: Ubuntu, 8 cores, about 500 processes, 66
mounts, 98 listeners, 774 connections, a containerd, snaps, a GNOME session. Nothing was set up
for this session. **Binary.** `target/debug/ono` at `05970a0` — a debug build, so every timing
impression below is pessimistic; the measured figures are in
`docker/acceptance/cases/100-spatial-performance-budgets.case`. **Agent.** `S11b`.

**Verdict on §52.3's statement, first, because it is the point of the exercise.**

> A technically experienced user can start on an unfamiliar Linux host, understand the major
> areas of the system, discover significant services/processes/filesystems/network endpoints,
> move through real relationships, return along the path taken, and observe live change without
> needing to know the object names or the traditional Unix inspection commands in advance.

**True for orientation and for hierarchy; it breaks at the first permission boundary.** I
oriented on this host without typing a single name, found a listening port I did not know
existed, and walked back out along my own trail — all of that worked as written, and `map` at
the root is a better answer to "what is this machine" than anything I would have typed by hand.
But at the moment a relationship crossed a boundary the kernel would not let me over, the shell
said **`process 0`** where the truth is "I may not see who owns this socket". A technically
experienced user is not merely unserved there; they are misled. That is finding 2 below, it is
the one release-relevant defect this session produced, and §2.17 and §35.2 both forbid it in
words.

---

## What I did

1. `look` at the root. Six domains, counts on each, a landmark list. Immediately readable.
2. `near` at the root, `look --json`, `map`. The root map — SYSTEM, the six domains, the
   collections under each, 30 nodes and a bounded marker — is the best single view in the shell.
3. `enter network`, `look`. Fourteen interfaces, 69 routes, 98 listeners, 774 connections;
   `addresses` and `namespaces` honestly `unsupported — no provider answers for …`; eight
   landmarks, all public listeners, one address in state `failed`.
4. `enter listeners`, `near`. Ports 22, 6556, 8080, 9510, 9512, 9513 and a page of unix sockets.
   **6556 I did not know.** So: `enter 0.0.0.0:6556`, `look` — and the trail stops, see below.
5. `find place --type process --where memory > 300MiB`, `… | take 1 | enter`, `look`,
   `follow sockets`, `back`, `up`, `trail --compact`. The pipeline-to-place composition of §28.2
   works exactly as the specification describes it.
6. Broke things on purpose: entered a process and killed it from inside the same session;
   entered a place, `stop process` on it; `follow` with an ambiguous relation; `up` at the root;
   `back` with an empty history; a predicate over a field that does not exist; a byte comparison
   with the wrong unit.
7. Ordinary Unix work in between — `ls`, `cd`, `pwd`, `git rev-parse` — interleaved with spatial
   moves in one session. Nothing about the shell got in the way; §2.15 holds.
8. `help look`, `help spatial`, `help here`, `map` from a process, `enter storage`.

## What was wrong

Numbered as they are filed in `docs/STATE.md`.

**1. `look`'s hidden count does not describe the list above it (§24.1, §24.2).** At the root
`look` prints the six domains and then `199 more not shown`. The 199 are neighbours — the 240
objects behind the collections, minus the 41 the neighbourhood drew — not domains. A reader
concludes the root has 205 exits. Either the count belongs to the neighbourhood section, or the
line has to say what it is counting.

**2. A group the provider answered `null` for is reported as `empty`, not as `unknown` (§2.17,
§35.2, AGENTS.md §6).** At `0.0.0.0:6556`, owned by uid 113, `look` says `process 0`. The
provider is honest: `get socket --listening` carries `"process": null`, because an unprivileged
process cannot read another user's socket owner — `ss -ltnp` shows the same blank. The spatial
layer turns that `null` into a group with `count: 0, state: "available"`, which is exactly
§35.2's own counter-example ("files 0" where the truth is a refusal). This is the finding that
breaks §52.3's statement, and it is in the territory ADR-0203's T17 is supposed to cover: the
row's tests all exercise a provider that *stated* a refusal, and none exercises a provider that
answered `null`.

**3. `find place --where` swallows both unknown fields and evaluation errors (§2.17, §29.3;
v0.2 §11.3).** `find place --type process --where nosuchfield == 1 | count` answers `0`, where
`get process | where nosuchfield == 1` refuses with `Ono-Sendai-E0202`. So does
`--where memory > 1`, which in the pipeline is `Ono-Sendai-E0203 cannot compare bytesize and
int` on every row. A typo in a script is indistinguishable from an empty system. I wrote the fix
(a pre-flight field check when *no* candidate target declares the field) and reverted it:
`docker/acceptance/cases/101-spatial-find-place.case` assertion `s3i` pins the present behaviour
as deliberate, and `TargetPlan::is_empty` defends it in prose, so reversing it is a contract
decision that needs its own ADR rather than a hardening commit.

**4. A multi-line diagnostic is rendered with `\u{a}` where its line breaks should be.**
`follow files` at a process with eleven open files prints the whole candidate list on one line
with a literal `\u{a}` between entries. The render boundary escapes control characters
unconditionally, which is ADR-0015's T1 and right for the file names embedded in that message —
and wrong for the newlines the shell itself put there. The list is unreadable exactly when it is
most needed.

**5. `help spatial` did not exist (§38.1).** A MUST, and the first page a user reaches for
before they know a verb to ask about. **Fixed in this session**, with an acceptance assertion in
case `102` (`s4t`, `s4u`). `help here` (§38.2, a SHOULD) is still absent and is filed.

**6. Every read-only mount is a "storage pressure" landmark (§26.2).** At STORAGE the landmark
list is nothing but snaps: `/snap/core24/1587 storage pressure — 100% used`, twenty of them. A
squashfs image is full by definition. The rule needs to exclude read-only filesystems, or the
landmarks of the storage domain are noise, which is §2.11's own failure mode.

**7. A map of a process is a flat list with duplicate labels (§23.5, §11.4).** `map` at
gnome-shell draws `also here` with eight rows all called `/run/user/1000/wayland-0`, one row
called `4026531836` (a pid namespace inode, unlabelled), and no relation on any of them. The
root map is excellent; the object map cannot be used to choose a neighbour, which is what a map
is for.

**8. `cpu` is `null` in every one-shot run, so "what is busy?" cannot be asked.** All 493
processes answer `cpu: null` from `ono -c`. It is not a lie — CPU is a rate, and
`ono-provider-linux`'s first observation has nothing to subtract from — but it means
`find place --where cpu > 5` is silence, and §26.2's high-CPU landmark can never fire outside a
session that has already observed the process once. A second `get process` in the same session
does produce values.

**9. `look --json | select <field>` fails two different ways.** `select name` refuses with
`unknown field name on PlaceView` (a pre-flight check against the declared record half of the
output type) and `select label` — a real field — fails at run time with `cannot read field
label on a value of type string`, because what `--json` writes is a string. The route is
`look --json | from json | select …`, which case `090` uses; nothing in either error says so.

**10. Two small ones.** `near --relation process` reports the four options and does not mention
that the relation is a positional selector (`near process`), which is the spelling that works.
And `near <relation>` with no neighbours prints nothing at all, so "no such neighbour" and "the
command did nothing" look the same.

## What I could not do

- Learn what is listening on port 6556 (finding 2). The shell showed me the port and then told
  me nothing owns it.
- Ask what is busy (finding 8).
- Reach `help here` (§38.2).
- See a tombstone from a script: the trail is session-local by design (§46.1), so each `ono -c`
  starts empty and a process that dies between two runs is simply not found. Correct, and worth
  knowing before reading §10.3 and expecting otherwise.

## What was slow

Nothing. On a 500-process host, in a **debug** build, no spatial command took long enough to
notice — `look`, `near`, `map`, `find place` and `enter` all answered inside a blink, and the
one-shot process cost is dominated by starting the binary. The container measurements agree:
`look` 178 µs warm, `map` L2 472 µs, `find place` 1.8 ms, startup indistinguishable from `bash`
under the same harness.

## What I corrected in the board

`docs/STATE.md` carried "`enter process <pid>` cannot reach a process started with `setsid`",
with the reproducer `setsid sleep 60 & ono -c "enter process $!"`. **It does not reproduce.**
`$!` there is `setsid`'s own pid, and `setsid` forks and exits immediately, so the pid being
looked for belongs to a process that no longer exists. Started properly —
`setsid tail -f /dev/null &` and then the child's real pid — `find place --type process --where
pid == <pid>` finds it and `enter <pid>` enters it. The entry is closed with this note.
