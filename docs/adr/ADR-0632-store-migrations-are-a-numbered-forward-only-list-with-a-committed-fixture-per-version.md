# ADR-0632: Store migrations are a numbered forward-only list with a committed fixture per version

- Status: accepted
- Date: 2026-09-09
- Spec refs: v0.5 §6.7, §18.4, §27.1, §31.6, §44.3; ADR-0620, ADR-0630
- Decided by: agent (autonomous)

## Context

§31.6 requires two things of migration: that it is versioned and "tested against fixtures from every
shipped v0.5 store version", and that it "MUST preserve `EventId`, `EvidenceId`, `ActionId` and
causal references".

v0.5 ships the first version, so the second requirement has nothing to test against unless something
is done about it. A migration harness with one version and no migration proves that the code can
count to one.

The first requirement interacts with §6.7, which makes persisted events append-only "except during
explicit storage migration that preserves semantic identity". Every identity in this tree is a
content digest (ADR-0620), so a migration that recomputed one would have changed what the event *is*.
The rule that keeps both requirements true is the same rule: a migration adds structure and never
touches an identity.

## Decision

### 1. Migrations are a list of numbered steps, applied in order, each in its own transaction

`STEPS` in `src/migrate.rs` is `[(version, sql)]`. A store at version `n` opened by an Ono shipping
version `m > n` runs steps `n+1 ..= m` and records the new number in `metadata.store_version` inside
the same transaction as the step. There is no down migration: §31.6 says versioned, and a downgrade
that discards a column discards history.

A store at a version this Ono does not know is refused with `temporal.store_unavailable`, and the
refusal says the shell keeps working without persistent history. That is §44.3 verbatim: "if
migration cannot complete safely, current shell operation continues with temporal persistent
functionality disabled and an explicit diagnostic."

### 2. v0.5 ships two versions, so the matrix is exercised rather than asserted

Version 1 is the schema of ADR-0630. Version 2 adds `events.significance` and the index
`events_by_significance (scope_path, significance, presentation_nanos)`.

The column is not invented for the migration's sake. §18.4 requires stepping to the next
*significant* event and §27.1 makes a landmark transition exactly such an event, and both queries
are "the next significant event in this place after this instant" — which cannot be answered without
decoding every payload in between unless the flag is a column. It is added now because adding it
later is the migration this ADR exists to make testable, and because a later phase needs it.

Existing rows take the default, which says only that nothing has yet classified them. No event
changes what it is, so §6.7 holds.

### 3. Every shipped version has a fixture committed as bytes

`tests/fixtures/ledger-v1.sqlite3` is a real version 1 store holding three events, two evidence
records, one causal link, one coverage interval, one redacted action and one checkpoint with an
object and a relation. `tests/migration.rs` reads every identity out of it with plain SQL, opens it
— which migrates it — reads them again, and asserts the two sets are equal. The identities are read
with SQL rather than through `LedgerRead` so the assertion does not depend on the code under test to
answer it.

The fixture is never regenerated by the test suite. A fixture a test can rewrite proves that the
code agrees with itself, which is not what §31.6 asks for. `tests/fixtures/README.md` records how it
was produced; the permanent definition of version 1 is `STEPS[0]`, which is forward-only and never
edited.

Every version this project ships gets a fixture under the same name, and the migration test grows a
case. That is the mechanism §31.6's "every shipped v0.5 store version" asks for.

## Consequences

Changing `STEPS[0]` after v0.5 ships is a defect, not a refactor: the committed fixture is what a
released store looks like, and editing the step that produced it makes the two disagree silently.
Later shapes are later steps.

The store version and the payload version (ADR-0630 §5) are separate numbers on purpose. The first
is the shape of the tables; the second is the shape of a blob. A change to one is not a change to
the other.

Tests: `tests/migration.rs` — five cases, including a v1 fixture that migrates with every identity
intact, a migrated store that is still writable, and a store from a newer Ono that is refused with
the §44.3 diagnostic.

## Alternatives considered

**Ship one version and assert the harness works.** Rejected by the brief and by §31.6: a migration
matrix with no migration in it is untested code that will first run on a user's data.

**Generate the fixture in a test fixture builder.** Rejected: it would test that today's code agrees
with today's code. The point of a committed fixture is that it was written by a version that has
stopped changing.

**A version-2 column invented purely to exercise the migration.** Rejected as dishonest scaffolding.
`significance` is a column §18.4 and §27.1 need; adding it now makes the migration real in both
directions.
