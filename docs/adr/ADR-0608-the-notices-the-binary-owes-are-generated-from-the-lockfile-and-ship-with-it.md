# ADR-0608: The notices the binary owes are generated from the lockfile and ship with it

- Status: accepted
- Date: 2026-09-08
- Spec refs: v0.2 §45.2; v0.4.1 §47.1, §50.3; ADR-0121, ADR-0123, ADR-0449, ADR-0607
- Decided by: agent (autonomous)

## Context

`deny.toml` answers one question about a dependency's licence — may this project ship it — and
ADR-0449 made that question part of the gate. It never answered the second one: once the binary is
in somebody else's hands, what do those licences ask to travel with it? MIT asks that its
permission notice do; Apache-2.0 §4 asks for its text and any `NOTICE`; and `CDLA-Permissive-2.0`
§2.1 asks that the agreement's own text travel with the data, which arrived with `webpki-roots`
and the Mozilla root store `ureq` verifies a plugin artifact against (ADR-0607).

The packages answered none of it: `crates/ono-cli/Cargo.toml` installed this project's own
`LICENSE` and nothing else. The obligation is older than the fetcher — Apache-2.0 dependencies
have been in the graph since the beginning — and it was recorded on the board rather than noticed
at a release.

A file somebody writes by hand is not a fix. It is correct on the day it is written and silently
wrong after the first dependency bump, and a notice file that has fallen behind says something
untrue about what is being distributed.

## Decision

### 1. The notices are a generated artifact, held to the lockfile by the gate

`THIRD-PARTY-LICENSES` at the repository root is generated by `cargo run -p xtask -- licenses
--write`, exactly as `docs/reference/` is generated by `… -- docs`. `spec-check` regenerates it and
compares, so the gate is red while it is stale, and `cargo run -p xtask -- licenses` without
`--write` reports the same thing on its own. A failure to read the graph is itself a problem
rather than a pass: what the project distributes is not something to be silent about.

### 2. What it covers: what the binary links, over every platform

The graph is walked from `ono-cli` — the package the `ono` binary comes from — through normal and
build dependencies, and never through dev-dependencies, because a test harness is not distributed.
A build dependency is included because what it generates reaches the binary.

It is deliberately **not** filtered by platform. The union over every target the lockfile resolves
is a superset of what any one build links, which is the safe direction for a notice, and it is the
only choice that yields the same file on the x86-64 and the aarch64 release runners — a
platform-filtered file would make the drift check fail on whichever architecture did not write it.

### 3. Every text once, and an absence stated rather than passed over

Two hundred crates ship the same Apache-2.0 text. Each distinct document is reproduced once, under
the crates that carry it, which turns 2.9 MB of licence files into 592 KB. Crates that ship no
licence document at all — twenty of the three hundred and eleven — get a section of their own
naming them with the expression they declare, because the difference between *we left it out* and
*upstream ships none* is the whole value of the file to somebody checking an obligation. Nothing
is invented for a crate that declares nothing; it is recorded as declaring nothing.

### 4. It ships in both packages

`/usr/share/doc/ono/THIRD-PARTY-LICENSES` in the `.deb` and
`/usr/share/licenses/ono/THIRD-PARTY-LICENSES` in the `.rpm`, beside the project's own `LICENSE`.
A notice file that never leaves the repository discharges nothing.

## Consequences

- A dependency change that adds a crate turns the gate red until the notices are regenerated,
  which is the same rhythm as adding a command and regenerating `docs/reference/`.
- The file is 592 KB of generated text in the repository and in each package. That is the cost of
  the obligation being real; a smaller file would be a shorter answer to a question that was not
  asked.
- Generation reads the crate sources cargo has already extracted under its registry. It runs no
  network and needs no additional tool, so the gate gains no dependency — `cargo-about` would have
  been a fourth pinned binary for something eighty lines of `xtask` already had the inputs for.
- Encoded by `xtask/tests/notices.rs` (the committed file agrees with the lockfile, both packages
  install it, the data licence's text is reproduced and its crate named, a crate shipping no
  document is named), the unit tests of `xtask::notices`, and `xtask/tests/packaging.rs`, which
  now expects the file in the built `.deb` and `.rpm`.

## Alternatives considered

- **A hand-written `THIRD-PARTY-LICENSES`.** Correct for a day. The gate cannot check a document
  whose source of truth is somebody's memory of the last `cargo update`.
- **`cargo-about`.** Does this well and would be a fourth version-pinned tool in the gate and in
  CI (ADR-0449 pins three), with a template language to maintain, for inputs `cargo metadata`
  already provides.
- **A list of crates and SPDX identifiers without the texts.** Names the obligation instead of
  discharging it: MIT asks for its notice, not for the string `MIT`.
- **Filtering to the release targets.** More precise about a single build and less stable across
  the two architectures we release for; a notice may be over-inclusive without being wrong.
