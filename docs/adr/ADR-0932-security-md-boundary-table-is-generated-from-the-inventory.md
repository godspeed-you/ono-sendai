# ADR-0932: SECURITY.md's boundary table is generated from the inventory

- Status: accepted
- Date: 2026-10-07
- Spec refs: v0.4.1 §6.1, §6.2, §20, §51.4, §52.2; spec §36.2; ADR-0546, ADR-0870, ADR-0915,
  ADR-0916
- Decided by: agent (autonomous)

## Context

v0.4.1 §6.1: the boundary inventory "MUST be derivable into documentation". It is:
`docs/reference/security-boundaries.md` is generated from
`docs/contracts/hardening/security_boundaries.yaml` and the gate compares the two (ADR-0546). But
`SECURITY.md`'s table, "The boundaries, in one page" — the page §51.4 calls the front door and the
one a reporter reads first — was typed by hand. A boundary renamed in the inventory left it silently
wrong (issue #170). It had already drifted in shape: it merged `provider.query` and `provider.act`
into one row, and it listed a thirteenth boundary — the compiled KUANG/11 component store
(ADR-0870, ADR-0915, ADR-0916) — that the inventory did not declare at all, so its claim "each has
an automated test that proves the forbidden thing is refused" was unchecked for that row.

`SECURITY.md` is prose a person writes; the table is the one part of it that restates a contract.
Its columns are deliberately plainer than the inventory's, whose `input_trust` and
`required_enforcement` are §6.1's words copied verbatim and held to them by the gate.

## Decision

1. **The table between two markers in `SECURITY.md` is generated by `cargo xtask docs`** from the
   inventory, by the same generator and the same `check_committed` comparison as
   `docs/reference/`. Everything outside the markers stays hand-written. The markers are
   `<!-- generated by `cargo xtask docs` from docs/contracts/hardening/security_boundaries.yaml:
   edit the inventory, not this table. -->` and `<!-- end generated -->`.
2. **Each boundary carries `front_door: {title, crosses, enforced}`** — the plain words the page
   uses — beside `doc`. A row is `| <title> (`<id>`) | <crosses> | <enforced> |`, so the inventory
   id is printed and a renamed boundary is a difference the gate reports at `SECURITY.md`.
3. **`check_security_boundaries` requires the three `front_door` fields** on every boundary, so a
   new boundary cannot render as a blank row.
4. **`check_committed` reports a `SECURITY.md` that exists without the markers**, so the table
   cannot be typed back in by hand.
5. **The compiled-component store is recorded in the inventory as `kuang.compiled.load`**: owner
   `ono-kuang-supervisor`, enforced in `crates/ono-kuang-supervisor/src/compiled.rs`, proved by six
   refusal tests of `crates/ono-kuang-sdk/tests/compiled.rs`. It is a boundary the repository
   added beyond §6.1's twelve, which `check_security_boundaries` admits (only the twelve are held
   to the specification's words); its `input_trust`/`required_enforcement` are this repository's.
6. `provider.query` and `provider.act` become two rows on the page, as they are two boundaries.

## Consequences

- A boundary renamed, added or reworded in the inventory changes `SECURITY.md` through
  `cargo xtask docs`, and `spec-check` is red until it is regenerated.
- `xtask/src/terminology.rs` keeps reading `SECURITY.md` as a whole; the generated rows are held to
  the same overstatement rules as the prose around them.
- `xtask/tests/reference.rs::should_render_a_boundary_page_that_matches_the_inventory` asserted
  exactly twelve boundaries while its message said "at minimum"; it was corrected to the floor in
  its own `test:` commit before the thirteenth was recorded.

Encoded by `xtask/tests/reference.rs`:
`should_generate_the_security_pages_boundary_table_from_the_inventory`,
`should_report_a_security_page_whose_boundary_table_disagrees_with_the_inventory`,
`should_report_a_security_page_that_carries_no_generated_boundary_table`,
`should_find_this_repositorys_committed_reference_docs_up_to_date_when_checked`; and
`xtask/tests/contracts.rs::should_report_a_boundary_that_gives_the_security_page_no_words`.

## Alternatives considered

- **Compare SECURITY.md's rows with the inventory without generating them.** It needs a mapping
  from each hand-written title to an id, which is the second truth again, and a check that can say
  "wrong" but not what is right.
- **Render §6.1's terse columns into SECURITY.md.** One source with no new fields, but the front
  door would read like the reviewer's table; §51.4 wants the page usable by someone who has not
  read the specification.
- **Drop the compiled-component row from the page.** Loses a boundary users rely on from the one
  page that lists them.
