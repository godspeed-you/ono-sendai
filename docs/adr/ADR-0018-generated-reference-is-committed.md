# ADR-0018: `docs/reference/` is generated and committed

- Status: accepted
- Date: 2026-08-26
- Spec refs: §36.2, §46; AGENTS.md §2, §12.2; `docs/ACCEPTANCE.md` §4.5
- Decided by: agent (autonomous)

## Context

AGENTS.md §12.2 says never to commit a generated artifact the generator can reproduce, "except
where CI needs them checked in — then say so in an ADR". `docs/ACCEPTANCE.md` §4.5 requires that
"generated documentation is reproducible from the registries **and committed docs match it**",
which cannot be checked against files that are not in the tree. The two rules point in opposite
directions, and `.gitignore` had resolved it by excluding `docs/reference/` entirely.

## Decision

`docs/reference/` is generated by `cargo xtask docs` and **is committed**. This is the exception
AGENTS.md §12.2 anticipates, taken for three reasons:

1. `docs/ACCEPTANCE.md` §4.5 is a release-blocking checklist item phrased in terms of committed
   files. Un-committing them would satisfy it by making it unmeasurable.
2. **A change to the public contract becomes reviewable as a diff.** Editing one line of
   `docs/contracts/commands/process.yaml` produces a visible change in the command reference, so a
   reviewer sees the consequence of a contract change rather than only its cause. That is the
   whole value of deriving docs from contracts, and it is invisible if the output never lands.
3. Someone reading the repository — on a web view, in a review, on a machine with no Rust
   toolchain — gets the reference. A contract nobody can read is a contract nobody checks.

The tree stays honest about it in three ways: every page carries a banner saying it is generated
and must not be hand-edited; `cargo xtask spec-check` regenerates the pages in memory and fails on
any difference, so a hand-edit turns the gate red; and generation is byte-reproducible, so the
comparison is exact rather than approximate.

Nothing else generated is committed. Build output, `target/` and future generated code stay out
of the tree, because none of them is a contract anyone reviews.

## Consequences

Easy: the reference is always present and always current; a contract change and its documented
consequence appear in the same commit; the checklist item is checkable.

Hard: a registry change now requires running `cargo xtask docs` before committing, or the gate
fails. That is the intended friction — the failure message names the command — and it is
strictly better than the alternative, where the docs drift and nobody notices for months.

Encoded by: `xtask/tests/reference.rs`, in particular the test that regenerates this
repository's pages and requires the committed files to be identical.

## Alternatives considered

- **Generating into `target/` and publishing from CI** — rejected: it satisfies neither reason 2
  nor reason 3, and it makes the release checklist item unverifiable in the repository that
  defines it.
- **Hand-writing the reference** — rejected outright by spec §36 and by AGENTS.md §2; it would
  drift from the registries within one phase.
