# ADR-0530: Provenance is what the workflow says, not what the build hands it

- Status: accepted
- Date: 2026-09-03
- Spec refs: v0.4.1 §47.1 (required release files), §47.4 (provenance), §62.5 (provenance
  verification), §66.7 (all published artifacts), §46.2 (no wall-clock build time), §49.1 (build
  once, promote after proof), §40.2 (the acceptance container has no network), Appendix H
- Issues: #108 — builds on #103 (ADR-0451), #106 (ADR-0528), #107 (ADR-0529)
- Decided by: agent (autonomous)

## Context

§47.4 lists seven things provenance binds, and then adds the sentence that decides how it is
built:

> The provenance MUST be generated by the trusted release workflow rather than supplied by
> untrusted build output.

ADR-0451 had already drawn the line this sits on. `dist/build-inputs.json` records what the build
was *given* — commit, tag, toolchain, lockfile hash, image digests, action commits, tool versions,
`SOURCE_DATE_EPOCH`, run identity — and that ADR ended by saying its limit out loud: the manifest
is a statement of intent, and an attestation of what physically executed belongs to §47. This is
that attestation.

§66.7 adds the failure it exists to prevent: provenance that binds the binary while the packages
go unattested.

## Decision

**`cargo xtask provenance` writes `dist/build-provenance.json` — an in-toto statement binding
§47.4's seven fields to every published artifact — and `--verify` refuses a release whose
manifest, provenance and bytes do not all agree.**

### Where each field comes from

Every field is read from the Appendix H input manifest or from the environment of the run that is
generating the document. **Nothing is read from the artifacts.** Where both can answer, the run
wins: a workflow can be trusted about its own identity, and a file that travelled with the build
cannot. That is §47.4's sentence, implemented as a precedence rule rather than as a comment.

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "predicateType": "https://github.com/godspeed-you/ono-sendai/provenance/v1",
  "subject": [{ "name": "ono_0.4.1_amd64.deb", "digest": { "sha256": "…" } }, …],
  "predicate": {
    "schema": "ono.build-provenance.v1",
    "repository": "…", "source_commit": "…", "release_tag": "…",
    "workflow": { "name": "release", "run_id": "…", "run_attempt": "…", "ref": "…", "runner": {…} },
    "builder": { "id": "https://github.com/…/.github/workflows/release.yml",
                 "toolchain": "1.94", "tools": {…} },
    "build_timestamp": "2026-09-02T08:35:12Z",
    "inputs": { "manifest": "build-inputs.json", "lockfile_sha256": "…", "containers": {…} }
  }
}
```

Three of these are decisions rather than transcriptions:

- **`builder.id` is the workflow identity a verifier already pins.** It is the same string
  `scripts/verify-release.sh` demands of the signature (ADR-0529), so "who signed this" and "who
  says it was built here" are one answer rather than two that can drift apart.
- **`build_timestamp` is `SOURCE_DATE_EPOCH`, rendered as RFC 3339 in UTC.** §46.2 forbids a
  wall-clock build time where a reproducible equivalent exists, and one does: the epoch every
  artifact in the release is already stamped with. A provenance dated by the moment it was written
  would disagree with the packages it describes, and would make the document itself
  unreproducible. The conversion is Howard Hinnant's civil-from-days, eight lines, rather than a
  date library added to a release-critical path for one format.
- **`SHA256SUMS` is a subject.** It is the file the signature covers and the file a reader
  trusts; provenance that bound the packages and not the manifest would leave the trusted file
  unattested. The signature bundles are not subjects — a signature over a document cannot be
  inside the document it signs.

### What `--verify` refuses

§62.5 asks that each artifact digest be present in checksum *and* provenance output before
publication. That is three checks, and all three run:

- an unbound field among the seven — refused by name;
- a published artifact that is not a subject, or a subject that is not in the release;
- a subject whose digest is not the artifact's, or a digest the checksum manifest and the
  provenance disagree about.

The release workflow's `publish` job runs them in the order §49.1 draws: download the tested
bytes, write the manifest, write the provenance, sign both, **verify the whole directory the way a
reader will**, and only then attach anything.

## Consequences

**The container proves it.** Case `199-release-provenance` makes a release out of the `ono`
binary the acceptance image built — a real artifact, not a fixture of one — runs the real
`xtask` over it, and checks it as an unprivileged user with networking disabled. It closes
§4.8.13's fourteenth family for the two halves that are decidable there, and it proves the third
by its absence: a release with no signature is *refused*, not silently reported as checksummed.
The acceptance image therefore now builds `xtask` as well and ships it as
`/usr/local/bin/ono-release-tool` beside `ono-verify-release`.

**The verification script works without a workspace.** `scripts/verify-release.sh` uses
`$ONO_XTASK` when a built release tool is handed to it and `cargo run` otherwise, because the
container and a release runner have no workspace to compile and a reader with the repository does.

**A local release check cannot produce provenance.** Outside a release run there is no tag and no
workflow identity, so two of the seven fields would be null and `--verify` would refuse — as it
should. `scripts/release-check.sh` therefore does not attempt one, and §62.5 is asserted where it
belongs: in the release job, and in case `199` against a fixture input manifest.

Encoded by `xtask/tests/provenance.rs::should_bind_all_seven_required_fields_to_every_artifact_
digest` and `::should_verify_every_artifact_digest_against_the_checksum_manifest_and_the_
provenance_before_publication`, and by acceptance case `199`.

## Alternatives considered

**Emit SLSA provenance through `actions/attest-build-provenance`.** It produces a well-known
predicate and it produces it from inside an action, which is the thing §43.2 asks to avoid for
critical release logic and §47.4 asks to avoid for provenance specifically. The predicate would
also be about the *action's* view of the build rather than about the input manifest this project
already publishes, so the two would have to be reconciled by a reader.

**Put the whole input manifest inside the predicate.** Appendix H says the manifest "MAY be
embedded in or referenced by provenance". Embedding it would duplicate a file that is already a
published, digested subject, and the duplicate would be the copy a reader believed. Referencing it
by name and repeating only the three facts a rebuild needs — lockfile hash, containers, toolchain —
keeps one source for each fact.

**Derive the digests from `SHA256SUMS` instead of from the files.** It would make the provenance
agree with the manifest by construction and stop it from being independent evidence. Reading the
bytes twice is what lets `--verify` find a manifest and a provenance that disagree, which is the
condition §62.5 is written against.

**Date the provenance with `date -u`.** One line, and it would put a wall clock into the one
document whose whole purpose is to be checkable later (§46.2).
